# 주간 도착예상 구현 계획

작성: 2026-09-28. 최초 상태: 계획 수립 완료.

2026-09-29: Orca 작업폴더의 P1/P2 로컬 구현 초안을 실제 `server/`로 복원했습니다.
아래 체크리스트는 단계별 전체 완료 조건이며, 복원만으로 완료 처리하지 않습니다.
실행 가능한 범위와 남은 작업은 [README](README.md)에 기록합니다.
P3/P4 앱 변경은 충돌로 인해 보존만 했으며 현재 앱에 적용되지 않았습니다.
설계 기준: [arrival-estimate-design.md](arrival-estimate-design.md).

기술 결정(2026-09-29): 사용자와 TypeScript 사용을 확정했습니다.
Node.js·pnpm 기반의 기존 구현을 이어가며 운영 실행 환경과 저장소/CDN은 P0에서 별도 확정합니다.

### 2026-09-29 P2 복구 기능 보완

- 성공 표본별 원자적 중간 저장과 재실행 시 누락 슬롯 재수집 구현.
- 경로·보정 버전·보정값·출처·유효기간으로 재사용 가능 여부 확인.
- 인증 실패·쿼터·실행/월간 예산·개별 응답 오류의 실패 사유 구분.
- 저장 실패는 API 재시도와 분리하고 실행 실패로 전달.
- 게시 이력 저장 후 중단된 동일 내용의 게시 재시도 지원, ID 충돌 시 기존 결과 보존.
- 단일 호스트 강제 종료 후 남는 잠금 파일의 복구 절차는 README에 기록.

검증: TypeScript 검사와 서버 테스트 15개 통과. 합성 CLI 실행에서 표본 499개를 생성했고,
같은 기간 재실행은 요청 0건·실패 0건으로 기존 결과를 재사용했습니다.

주간 예약 실행·운영 저장소/CDN·분산 잠금은 미구현이며 P2 전체 완료로 처리하지 않습니다.

## 첫 출시 범위

- 4개 방향과 확인된 경유편의 종점 예상 도착시간 제공.
- 주 1회 다음 7일의 시간대별 예측 수집, 모든 사용자에게 동일한 JSON 배포.
- 앱의 홈·운행 목록·상세·Live Activity에서 같은 운행편 계산 결과 사용.
- 예측이 없거나 유효하지 않으면 기존 시간표 기본 소요시간 사용.
- 차량 위치 추적, 실제 출발 지연 감지, 중간 정류장 예측, 관리자 웹,
  장기 통계 학습은 후속 범위로 둔다.

## 구현 순서와 완료 조건

### P0. 제공사·경로 검증과 운영 방식 결정

- [ ] API 결과 7일 저장, 사용자 간 공유, 버스 보정 결과 제공 가능 여부를 기록한다.
- [ ] 미래 7일 조회 범위와 실제 계정의 권한·쿼터를 확인한다.
- [ ] 4개 방향과 경유편의 실제 경로·정류장 순서를 확정한다.
      기존 timetable.json의 path는 대조 자료로 사용하고 실제 운행 경로인지 확인한다.
- [ ] 최소 표본으로 평일 혼잡/비혼잡·주말의 반환 경로와 소요시간을 검토한다.
- [ ] 서버 배포 후보인 예약 실행 + 객체 저장소/CDN의 요금·계정 조건을 비교해 확정한다.
      기존 후보 Cloudflare Workers를 우선 검토하되 실행기와 저장소는 교체 가능하게 분리한다.

완료 조건: 결과·출처·확인일을 기록한 provider-validation.md와 검증된 경로 설정.
확인 전에도 P1 및 합성 fixture 기반 P2/P3 구현은 진행할 수 있다.
외부 제공사 문의 발송이 필요하면 별도 발송 지시를 받는다. 실제 데이터 공개는 조건 확인 후 진행한다.

### P1. 데이터 계약과 경로 설정

- [ ] TypeScript 기반 server 패키지와 검사·테스트·로컬 실행 명령을 만든다.
- [ ] schemas/arrival-estimates.schema.json에 앱과 서버의 공통 계약을 정의한다.
- [ ] config/routes.json에 routeId, variantId, 경유지, routeVersion,
      보정값(초), correctionVersion, 수집 간격을 정의한다.
- [ ] 변형 구분은 시간표의 via_times와 매핑한다. 경로가 미확정인 경유편은 기본값만 제공한다.
- [ ] 검증된 경로 버전을 시간표에 선택 필드로 추가하고 신규 앱에서 일치를 확인한다.
      기존 시간표 URL·필드는 유지한다. 버전이 없는 시간표는 기본값을 사용한다.
- [ ] fixtures/에 정상·누락·만료·공휴일·경유편·잘못된 버전의 합성 데이터를 만든다.

계약 필드:

| 수준 | 필드 |
|---|---|
| 문서 | schemaVersion, snapshotId, generatedAt, timezone, validFrom, validUntil, enabled |
| 경로 | routeId, variantId, routeVersion, correctionVersion |
| 표본 | serviceDate, departureMinute, durationSeconds, correctionSeconds, fetchedAt, source |

durationSeconds는 도로 예측 원본 소요시간이며 correctionSeconds는 별도 가산한다.
보정을 중복 적용하지 않는다. 저장 기간은 확인된 제공사 허용 기간을 넘지 않는다.
validUntil은 배타적 경계이며 서버·앱 모두 KST 운행일을 사용한다.

완료 조건: 서버 검증기와 Swift 디코더가 동일한 합성 fixture를 해석하고,
중복 키·음수 시간·알 수 없는 필수 스키마 버전은 거부한다.

### P2. 주간 수집기와 안전한 게시

- [ ] src/provider.ts: 외부 요청·오류 변환을 담당하는 교체 가능한 인터페이스.
- [ ] src/schedule.ts: 다음 7일의 실제 운행 시간대를 요청 목록으로 생성.
      1시간 간격을 기본으로 첫차·막차 표본을 포함하고 경유편은 필요한 시각만 조회한다.
- [ ] src/collect.ts: 제한된 동시 요청, 시간 제한, 호출 예산, 실패 재시도 구현.
      401/403은 중단, 429는 해당 실행에서 추가 요청 중단, 5xx/일시 오류만 최대 2회 재시도한다.
- [ ] src/validate.ts: 경로·시간 범위·중복·누락·경로 버전 검증.
      경로 이탈 판단에 필요한 상세 응답을 수집하되 원본 장기 저장은 기본 비활성화한다.
- [ ] src/publish.ts: 불변 스냅샷 업로드 후 latest 포인터를 갱신한다.
      게시 실패 시 기존 포인터를 유지하고 동시 실행은 잠금 또는 조건부 갱신으로 제어한다.
- [ ] 주간 작업은 일요일 저녁 실행해 다음 월~일 운행일을 대상으로 한다.
      이전 스냅샷의 아직 유효한 일요일 데이터도 앱에서 사용할 수 있게 보존한다.
      제공사 조회 범위에 맞지 않으면 운영 시각·대상 범위를 조정한다.
- [ ] 누락은 명시적으로 기록한다. 재실행 시 성공 표본 재호출을 줄이고 실패 슬롯만 재시도한다.
- [ ] dry-run은 호출 목록과 예상 건수만 출력하며 키·실데이터·공개 게시를 필요로 하지 않는다.

완료 조건: 합성 응답으로 일주일 결과 생성, 부분 실패, 요청 상한, 재실행,
게시 도중 실패 및 동시 실행을 검증한다. 사용자 조회는 외부 API 요청을 유발하지 않는다.

### P3. 앱 데이터 로딩과 운행편 계산

- [ ] Models/ArrivalEstimateSnapshot.swift: 스냅샷 및 결과 모델 추가.
- [ ] Services/ArrivalEstimateService.swift: 다운로드·영속 캐시·스키마 검증.
      URLSession·시계·저장소를 주입해 테스트 가능하게 한다.
- [ ] 별도 HTTP 계층에서 ETag/304를 처리한다. 기존 NetworkService는 2xx 전용이므로
      빈 304 응답을 JSON 디코딩하도록 재사용하지 않는다.
- [ ] 앱 활성 시 마지막 성공 확인 후 24시간이 지나면 조건부 갱신한다.
      날짜별 데이터가 없을 때는 조기 갱신하되 실패 백오프로 반복 호출을 제한한다.
      중복 다운로드는 합치고 앱 재시작에도 캐시를 유지한다.
- [ ] Services/ArrivalEstimateCalculator.swift: 출발일시·노선·경유편별 순수 계산.
      같은 날짜·경로의 인접 표본만 보간하며 간격이 설정 한도를 넘으면 기본값 사용.
      경계 밖으로 외삽하지 않는다. 초 단위 계산 후 화면 표시 시 분 단위로 올림한다.
- [ ] 계산 결과에 arrivalDate, durationSeconds, source, generatedAt, fallbackReason을 포함한다.
- [ ] 만료·누락·잘못된 경로 버전·공휴일 누락은 기존 duration_minutes로 복귀한다.

완료 조건: 서버·Swift 공통 fixture, 자정과 익일 도착, KST가 아닌 기기 시간대,
공휴일, 경유편, 한쪽 표본 누락, 오프라인·304·깨진 캐시 테스트 통과.

### P4. 화면과 Live Activity 통합

- [ ] MainViewModel의 trafficDurationMinutes와 effectiveDurationMinutes 단일값 구조를
      운행편별 계산으로 교체하고 TrafficService 직접 호출을 제거한다.
- [ ] makeBusDetailInfo, nextBusArrivalTime, buildUpcomingBuses와 Live Activity 시작 경로에
      동일한 계산 결과를 전달한다. direction 변경 중 이전 요청 결과가 섞이지 않게 한다.
- [ ] 실제 날짜 없이 평일/주말 시간표를 미리 보는 경우는 기본 소요시간을 사용한다.
      오늘과 다른 시간표 유형을 선택했다고 오늘 교통 예측을 적용하지 않는다.
- [ ] 실제로 확인되지 않은 지연 상태 및 임의 +5분 가산을 점검하고,
      이번 예측에 측정된 지연인 것처럼 혼합하지 않는다.
- [ ] 홈·목록·상세에 예상값 출처를 일관되게 제공한다.
      예측 사용 시 `요일·시간대 기반 예상`, 기본값 사용 시 `시간표 기준`으로 표시한다.
- [ ] LiveActivityService는 시각 문자열 대신 확정된 departureDate/arrivalDate를 전달받게 한다.
      활성 운행의 예상값은 시작 시 고정하고 다음 실행부터 새 스냅샷을 적용한다.
      Live Activity 표현도 차량 위치나 실제 도착 확인으로 오해되지 않게 점검한다.
- [ ] 일반 위젯에서 도착예상을 표시하는 사용처가 있다면 같은 계산을 사용한다.
      출발시간만 표시하는 위젯에는 불필요한 네트워크 작업을 추가하지 않는다.

완료 조건: 같은 운행편의 홈·목록·상세·Live Activity 예상 도착 일치,
빠른 방향 변경·날짜 변경·기본값 복귀 시 정상 표시. 기존 시간표·출발 알림 회귀 없음.

### P5. 배포와 운영 검증

- [ ] 확정한 환경에 스케줄·저장소·HTTPS 경로·비밀값·호출 예산 설정.
- [ ] 게시 전에 수동 1회 실행으로 표본·최종 JSON·앱 다운로드를 확인한다.
- [ ] 실행별 성공/실패 건수, 누락률, 마지막 성공 시각, 월간 API 건수를 기록한다.
- [ ] enabled=false 및 이전 스냅샷 포인터 복구로 중단·롤백을 검증한다.
      오프라인 앱에는 원격 중단이 즉시 전달되지 않으므로 유효기간 검증을 항상 적용한다.
- [ ] 개발용 합성 데이터가 운영에 게시되지 않도록 환경과 게시 경로를 분리한다.
- [ ] 2~4주 실제 출도착 표본으로 기존 고정시간 대비 오차를 비교한다.
      방향·혼잡도·요일별 표본 수를 함께 기록하고 표본 부족 구간은 판단을 보류한다.

완료 조건: 조건 확인된 데이터만 게시, 장애 시 기본값 복귀, 호출 예산 준수,
핵심 단위 테스트와 관련 화면 스모크 테스트 통과. 실측 결과를 근거로 일반 공개 범위를 결정한다.
기존 노후 UI 테스트 실패는 별도 기록하되 이번 변경의 회귀와 구분한다.

## 작업 단위와 의존성

1. P1 데이터 계약·합성 fixture
2. P2 로컬 수집기·검증·게시 어댑터
3. P3 앱 캐시·계산기
4. P4 화면·Live Activity 통합
5. P0 외부 조건 확인 결과를 반영한 실 API 어댑터·배포 환경 확정
6. P5 운영 배포·실측 평가

각 단위는 독립적으로 검토 가능한 커밋으로 나누되 공유 계약 변경을 먼저 반영한다.
P0는 최초 착수 때 조사하고 외부 확인 대기 중에는 합성 데이터로 1~4를 진행한다.
본 계획 작성 단계에서는 외부 API 호출, 유료 서비스 생성, 배포를 수행하지 않는다.

## 후속 범위

- 관측 결과에 따른 특정 시간대 30분 수집 또는 갱신 주기 단축.
- 허용된 보관 범위 내 요일별 장기 프로필 및 자체 실측 데이터 활용.
- 조회 상태·보정값을 관리하는 인증된 admin UI.
- 구간별 누적시간이 확보된 뒤 중간 정류장 도착예상.
