# 주간 갱신 도착예상 설계안

작성: 2026-09-28. 상태: 설계 제안, 구현·배포 전.

## 목표와 전제

고정된 버스 노선의 요일·시간대별 소요시간을 주 1회 갱신하고 모든 앱이 공유한다.
실제 차량 위치나 출발 지연은 추적하지 않는다. 화면 명칭은 `예상 도착`으로 하고
`요일·시간대 기반 예상` 및 갱신일을 제공한다. 짧은 노선의 반복성은 검증할 가설이며
정확도를 보장하는 근거로 삼지 않는다.

## 수집 방식

- 주 1회 예약 작업에서 다음 7일의 미래 출발시각별 예상 소요시간을 수집한다.
- 주 1회 실행과 API 요청 1건은 다르다. 노선·방향·경유편·날짜·시간대별 요청이 필요하다.
- 현재 시점 길찾기 응답 하나를 일주일 전체에 적용하지 않는다.
- 첫 버전은 운행시간 내 1시간 간격, 혼잡 변화가 큰 구간은 검증 후 30분 간격으로 세분화한다.
- 미래 예측 API의 조회 가능 기간·권한·실제 응답을 먼저 확인한다. 7일 조회가 불가능하면
  가능한 날짜만 수집하고 실행 주기를 조정한다. 현재값을 미래값으로 대체하지 않는다.
- 날짜별 예측을 우선 사용한다. 여러 주의 값을 요일별로 합치는 기능은 저장 허용 범위와
  실측 검증 후 도입한다. 명절·공휴일·임시 운행일을 일반 요일 표본에 섞지 않는다.

## 경로와 버스 보정

현재 시간표에는 방향을 구분한 4개 노선과 별도 경유편 정보가 있다.
데이터 키는 `routeId + variantId + routeVersion + serviceDate + departureMinute`로 한다.
시간대는 Asia/Seoul을 사용한다.

자동차 미래 길찾기를 후보로 쓰되 실제 버스 경로를 통과하는 경유지와 반환 경로를 검증한다.
추천 최단경로가 실제 버스 노선과 다르면 그 결과를 채택하지 않는다.
대중교통 길찾기는 고정 버스편 소요시간·해당 노선 지원 여부를 확인한 뒤 비교한다.
승용차 예상시간에 버스 정차·승하차 보정을 더하되, 보정값은 노선별 관측으로 정한다.
차종 옵션만으로 버스전용차로·정차가 반영된다고 가정하지 않는다.

예상 도착 = 시간표 출발일시 + 해당 출발시각의 예측 소요시간 + 버스 보정시간.
인접 시간대 값은 같은 날짜·같은 경로 버전일 때만 보간한다.
각 운행편의 출발시각을 기준으로 계산하며 현재 시각의 소요시간을 모든 편에 쓰지 않는다.
중간 정류장 도착예상은 구간별 누적시간을 확보한 뒤 지원한다. 종점 값을 거리 비례로 나누지 않는다.

## 최소 운영 구조

예약 작업 → 외부 API → 응답·경로 검증 → 버전 있는 JSON 저장 → CDN → 앱 로컬 계산.

- 상시 실행 서버와 사용자별 외부 API 호출은 필요하지 않다. 예약 실행 환경과 정적 배포를 사용한다.
- 첫 버전은 DB 없이 JSON으로 운영 가능하다. 저장소·CDN 공급자는 비용과 이용조건 확인 후 정한다.
- API 키는 예약 작업의 비밀값 저장소에만 둔다.
- 앱은 하루 1회 정도 조건부 갱신하고 캐시를 재사용한다. 화면 카운트다운은 로컬에서 처리한다.
- 스냅샷에는 schemaVersion, routeVersion, generatedAt, validFrom, validUntil,
  날짜별 예측값, 출처, 보정값 버전을 포함한다. 누락값은 0이 아니라 누락으로 표현한다.
- 검증이 끝난 파일만 원자적으로 게시한다. 부분 실패는 해당 슬롯만 누락 처리하고
  이전 데이터의 생성시각을 갱신된 것처럼 바꾸지 않는다.
- 앱은 유효한 날짜별 예측 → 허용된 유효 요일별 프로필(후속) → 기존 기본 소요시간 순으로 복귀한다.
  만료·경로 변경 시 기본값을 사용하고 화면에 `시간표 기준`을 표시한다.
- 공휴일 예측이 없으면 기본값으로 복귀한다. 일요일 교통 패턴으로 자동 치환하지 않는다.
- 관리자 UI는 후속으로 추가한다. 첫 단계는 설정 파일로 보정값·수집 간격·일시 중단을 관리한다.

## 호출량과 비용 예시

가정: 경로 변형을 제외한 4개 방향, 하루 18개 시간대, 7일.

- 주간: 4 × 18 × 7 = 504건.
- 월평균: 504 × 52 / 12 = 2,184건.
- 30분 간격이면 약 2배, 경유편·구간별 추가 조회·재시도는 별도 가산한다.
- 카카오 공식 가격표의 미래 길찾기 무료 일일 제공량은 5,000건,
  무료 쿼터 초과분 첫 가격 구간은 건당 8원이다(2026-09-28 확인).
- 예시 전체가 유료라면 월 17,472원. 무료 조건과 공통 월간 쿼터 충족 시 예시 API 비용은 0원일 수 있다.
  실제 앱의 다른 API 사용량·계약·활성화 조건을 확인해야 한다.
- 서버 비용은 예약 실행·저장·CDN 전송량의 합이다. 사용자 증가에 따라 CDN 비용은 늘 수 있지만
  외부 길찾기 API 요청 수는 늘지 않는다. 공급자 선정 전 무료 운영을 확약하지 않는다.
- 작업별 최대 요청 수, 제한된 재시도, 월간 호출 상한을 설정한다.
  인증 실패·쿼터 소진은 반복 재시도하지 않고 기본값으로 복귀한다.

## 구현 전 확인 및 검증

1. 제공사에 응답의 7일 저장, 앱 사용자 간 공유, 보정·집계 결과 제공 허용 여부 확인.
   공개 문서 조사만으로 이 조건은 확정하지 못했다. 금지 시 보관 기간을 단축하거나
   자체 운행 관측 기반 프로필로 전환한다.
2. 각 방향·경유편의 실제 버스 경로와 API 경로 비교. 정차·버스전용차로 차이 점검.
3. 2~4주간 혼잡/비혼잡·평일/주말을 포함해 실제 출도착을 수동 기록한다.
   시간표 대비 출발 지연과 주행시간 오차를 분리해 측정한다.
4. 기존 고정시간과 주간 예측의 평균 절대오차·큰 오차 빈도를 비교한다.
   잠정 목표는 ±5분 이내 80%이며 사용자와 조정할 제품 목표일 뿐 현재 성능이 아니다.
5. 개선되는 경우 주간 방식을 유지하고, 오차가 큰 시간대만 갱신·샘플 간격을 늘린다.
   관측 없는 오차 범위를 통계적 신뢰구간처럼 표시하지 않는다.

## 현재 코드에서 필요한 변경

- TrafficService의 앱 직접 호출 및 20분 메모리 캐시를 스냅샷 다운로드·영속 캐시로 교체.
- MainViewModel의 단일 trafficDurationMinutes 대신 운행편 출발일시별 계산 적용.
- 기존 시간표 JSON 경로와 기본 duration_minutes는 유지.
- 관련 `실시간` 표기를 실제 데이터 성격에 맞게 조정.
- 날짜 경계·공휴일·경유편·만료·부분 누락·네트워크 실패·경로 버전 불일치 검증.
